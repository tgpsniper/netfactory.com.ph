1. Overview & Business Case

Currently, each subscriber record in the system represents both a person and a service connection. This means a single customer who wants two internet connections (e.g., home + business, parent paying for a child's unit, business with multiple branches) must be registered as two completely separate subscribers with duplicate personal information.

Problems This Creates

  • Duplicate personal data (name, email, phone, IDs) across multiple records
  • Customer must maintain separate portal logins for each connection
  • No unified view of a customer's total relationship with Netfactory
  • Email/phone uniqueness constraints block creating a second account for the same person
  • CRM staff cannot see all connections belonging to one customer at a glance

Proposed Solution

Separate the person (subscriber) from the service connection (account). One subscriber can hold multiple accounts, each with its own plan, address, billing, equipment, and status.

2. Current Architecture

Today, the subscribers table is a monolithic record containing both personal identity and service connection data:

subscribers (current - single table) +-- id (PK) +-- account_number (unique) [ Person fields ] +-- first_name, last_name, email, phone +-- id_type, id_number [ Service fields ] +-- status, plan_id, ont_serial +-- address, barangay, municipality +-- balance, credit_balance +-- next_bill_date, installed_at +-- All child tables (invoices, payments, tickets, etc.) point here
Key issue: Every child table (invoices, payments, tickets, work orders, RADIUS, etc.) uses subscriber_id as its foreign key. The system cannot distinguish between "this invoice belongs to this person" vs. "this invoice belongs to this service connection."

3. Proposed Architecture

subscribers (person) subscriber_accounts (service connection) +-- id (PK) +-- id (PK) +-- first_name, last_name +-- subscriber_id -> subscribers (FK) +-- email, phone +-- account_number (unique) +-- id_type, id_number +-- status, plan_id +-- documents (IDs, proof) +-- address, barangay, municipality +-- created_at, updated_at +-- ont_serial, router_serial, mac_address +-- balance, credit_balance subscriber_auth (1:1 with person) +-- next_bill_date, installed_at +-- subscriber_id -> subscribers +-- agent_id, installation_package +-- password, 2FA, session +-- created_at, updated_at One Person -> Many Accounts -> Each account has own invoices, payments, tickets, etc.

5. Data Migration Strategy

Critical: This migration restructures the core data model. A full database backup must be taken before execution. Test on staging environment first.
StepActionDetail
1 Create subscriber_accounts table New table with all service-related columns. No data yet.
2 Populate subscriber_accounts For each existing subscriber, create one subscriber_accounts row copying all service fields. Set subscriber_accounts.subscriber_id = subscribers.id. This creates a 1:1 mapping — every existing subscriber gets exactly one account.
3 Add account_id column to child tables Add nullable account_id FK to: invoices, payments, subscriber_credits, tickets, usage_data, work_orders, surveys, onu_inventory, olt_onu_mappings, nap_ports, accounts_receivable, subscriber_radius.
4 Backfill account_id Using the 1:1 mapping from Step 2, set account_id in every child row based on its existing subscriber_id.
5 Make account_id non-nullable After backfill verification, add NOT NULL constraint on account_id in the child tables that were re-pointed.
6 Remove service columns from subscribers Drop: account_number, status, plan_id, address fields, equipment fields, balance fields, billing date fields, agent fields, remarks. Do this last, after all API code is updated.
7 Remove @unique from email Allow same email to be used across subscribers.
Key guarantee: After Step 2, every existing subscriber has exactly one account. Nothing breaks. Multi-account capability is only available for new additions after migration completes.

Account Switching Flow

  • Subscriber logs in with credentials — JWT contains subscriberId (person)
  • Portal fetches all subscriber_accounts for that person
  • Dropdown shows accounts: J2-00123 (Active - Plan 999), J2-00456 (Active - Plan 1499)
  • Selecting an account sets the accountId context for all subsequent views
  • "All Accounts" option shows consolidated data

Security Considerations

  • JWT only grants access to accounts owned by the authenticated subscriberId
  • Account selection validated server-side: subscriber_accounts.subscriber_id === req.subscriberId
  • Audit log records which account was accessed in each action
  • Account number login still works — resolves to the person via subscriber_accounts → subscribers

13. Implementation Phases

Phase 1 — Schema & Migration

  • Create subscriber_accounts table in Prisma schema
  • Write migration script to split existing subscriber data
  • Add account_id FK to all child tables and backfill
  • Remove @unique from email field

Risk: HIGH — Core schema change. Requires full DB backup and staging test.

Phase 2 — API Route Updates

  • Update all Prisma queries to use account_id instead of subscriber_id where re-mapped
  • Remove email/phone uniqueness checks from admin.js, portal.js, public.js, agents.js
  • Fix CRM Caller ID Lookup (findFirst → findMany)
  • Update invoice generation to iterate subscriber_accounts
  • Add new endpoints for account management

Risk: HIGH — Touches every route file. Must be done carefully with testing.

Phase 3 — CRM Frontend

  • Update subscriber list to show person + account count
  • Update subscriber detail to show person header + account tabs
  • Update "Add Subscriber" flow to: find/create person → add account
  • Add "Add Account" button on subscriber detail page
  • Update search to resolve account numbers to person view

Risk: MEDIUM — UI rework, but data layer already updated in Phase 2.

Phase 4 — Portal Frontend

  • Update login to support email/phone-based authentication
  • Add account selector dropdown in navigation
  • Add "My Accounts" page listing all accounts
  • Update dashboard, invoices, tickets views for account context
  • Add consolidated "All Accounts" view for invoices

Risk: MEDIUM — Auth flow change. Keep account_number login as fallback.

Phase 5 — Testing & Cleanup

  • End-to-end testing: create person, add multiple accounts, verify billing, portal login, tickets
  • Verify Xendit webhook chain works with new FK structure
  • Verify RADIUS authentication per account
  • Drop legacy service columns from subscribers table (after full verification)
  • Update any remaining hardcoded subscriber_id references

Risk: LOW — Cleanup and verification only.
